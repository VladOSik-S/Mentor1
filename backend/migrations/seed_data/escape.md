## Что такое Escape Analysis

**Escape analysis** (анализ побегов) — это процесс, который выполняет компилятор Go на этапе компиляции для определения места размещения переменных в памяти: на **стеке** (stack) или в **куче** (heap). Компилятор анализирует код статически и принимает решение на основе того, как переменная используется в программе.

Термин "escape" (побег) означает, что переменная "убегает" за пределы своей функции и должна быть размещена в куче, а не на стеке.

## Stack vs Heap: ключевые отличия

### Stack (Стек)

- **Быстрое выделение памяти**: добавление и удаление данных происходит за O(1)
- **Автоматическая очистка**: память освобождается автоматически при выходе из функции
- **Ограниченный размер**: стек имеет фиксированный размер для каждой горутины
- **Нет работы GC**: сборщик мусора не обрабатывает стек

### Heap (Куча)

- **Медленное выделение**: требует работы аллокатора памяти
- **Управление через GC**: требуется участие сборщика мусора для освобождения памяти
- **Неограниченный размер**: ограничен только доступной памятью системы
- **Накладные расходы**: GC может использовать до 25% CPU и создавать микросекундные паузы "stop the world"

## Когда переменная "убегает" в кучу

Переменная размещается в куче в следующих случаях:

### 1. Возврат указателя на локальную переменную

```
func createUser() *User {
    u := User{Name: "John"}
    return \&u  // u "убегает" в кучу
}
```

Переменная `u` должна жить дольше, чем функция `createUser`, поэтому компилятор размещает её в куче.

### 2. Хранение в интерфейсе

```
func storeInInterface(val int) interface{} {
    return val  // val убегает в кучу
}
```

Интерфейсы непрозрачны для компилятора, поэтому значения внутри них размещаются в куче.

### 3. Захват замыканием или горутиной

```
func process() {
    x := 42
    go func() {
        fmt.Println(x)  // x убегает в кучу
    }()
}
```

Переменная `x` захватывается анонимной функцией, которая может выполняться после завершения `process()`.

### 4. Хранение в глобальной переменной

```
var global *int

func setGlobal() {
    x := 100
    global = \&x  // x убегает в кучу
}
```

Переменная `x` должна жить дольше функции, так как на неё ссылается глобальная переменная.

### 5. Слишком большой размер

```
func createLargeArray() {
    arr := [1_000_000]int{}  // может убежать в кучу
    // ...
}
```

Если объект слишком велик для стека (обычно больше 64 КБ), компилятор размещает его в куче.

### 6. Отправка в канал

```
func sendToChannel(ch chan *int) {
    x := 42
    ch <- &x  // x убегает в кучу
}
```

Значение может пережить выполнение функции, так как оно передаётся в канал.

## Как проверить результаты Escape Analysis

Go предоставляет флаг компилятора для просмотра решений escape analysis:

```
# Базовый анализ

go build -gcflags="-m" ./...

# Детальный анализ (2 уровня)

go build -gcflags="-m -m" ./...

# Для одного файла

go run -gcflags="-m" main.go
```

### Пример вывода

```go
package main

func noEscape() int {
    x := 42
    return x  // остаётся на стеке
}

func escape() *int {
    x := 42
    return \&x  // убегает в кучу
}
```

Вывод компилятора:

```
./main.go:8:2: moved to heap: x
```

Это означает, что переменная `x` из функции `escape()` была перемещена в кучу.

## Семантика значений vs семантика указателей

### Семантика значений (Value Semantics)

```
func createUserV1() User {
    u := User{Name: "Bill"}
    return u  // возвращается копия, остаётся на стеке
}
```

Функция возвращает копию значения. Каждая функция получает свою собственную копию.

### Семантика указателей (Pointer Semantics)

```
func createUserV2() *User {
    u := User{Name: "Bill"}
    return \&u  // возвращается указатель, u убегает в кучу
}
```

Функция возвращает указатель на значение, которое будет размещено в куче.

## Читаемость кода и оператор &

Оператор `&` улучшает читаемость, показывая, что значение "расшаривается" (shared):

```
// Плохо: неясно, что происходит
var u *User
err := json.Unmarshal(data, \&u)
return u, err

// Хорошо: ясно видно расшаривание
var u User
err := json.Unmarshal(data, \&u)
return &u, err  // оператор \& явно показывает escape
```

Замените мысленно `&` словом "расшарить" при чтении кода — это помогает понять поведение памяти.

## Оптимизация и best practices

### Когда стоит избегать escape

1. **В критичных к производительности путях**: уменьшение heap allocations в горячих циклах снижает нагрузку на GC
2. **Для коротко живущих объектов**: они эффективно размещаются на стеке
3. **Когда профилирование показывает узкие места GC**: escape analysis помогает найти проблемные аллокации

### Когда escape допустим

1. **Конструкторы и фабрики**: возврат указателя из `NewThing()` — идиоматичный Go
2. **Объекты должны жить дольше функции**: расшаривание необходимо и корректно
3. **Редкие аллокации**: если аллокация не в горячем пути, оптимизация не критична
4. **Ухудшение читаемости**: не стоит жертвовать понятностью кода ради микрооптимизации

## Влияние на производительность

### Benchmark: Stack vs Heap

```
type Data struct {
    A, B, C int
}

// Аллокация на стеке
func StackAlloc() Data {
    return Data{1, 2, 3}
}

// Аллокация в куче (если действительно убегает)
var sink *Data

func HeapAlloc() {
    d := &Data{1, 2, 3}
    sink = d  // принудительный escape
}
```

Результаты бенчмарка:

- **StackAlloc**: 0.26 ns/op, 0 B/op, 0 allocs/op
- **HeapAlloc**: 10.55 ns/op, 24 B/op, 1 allocs/op

Heap-аллокация в ~40 раз медленнее и создаёт работу для GC.

## Важные термины для собеседований

- **Escape Analysis** — статический анализ компилятора для определения места размещения переменных
- **Stack allocation** — размещение на стеке, быстрое и без участия GC
- **Heap allocation** — размещение в куче, требует работы GC
- **GC pressure** — нагрузка на сборщик мусора из-за heap allocations
- **Value semantics** — семантика значений, работа с копиями
- **Pointer semantics** — семантика указателей, расшаривание через указатели
- **Inlining** — встраивание функций, может влиять на escape analysis
- **Stack frame** — фрейм стека, область памяти для функции
- **Static code analysis** — статический анализ кода на этапе компиляции

## Частые вопросы на собеседованиях

### Вопрос 1: Что такое escape analysis и зачем он нужен?

**Ответ**: Escape analysis — это процесс компилятора Go, который определяет, можно ли разместить переменную на стеке или она должна "убежать" в кучу. Цель — максимизировать stack allocations для уменьшения нагрузки на GC и улучшения производительности. Если переменная не покидает область видимости функции, она остаётся на стеке. Если она расшаривается за пределы функции (возврат указателя, передача в горутину), она размещается в куче.

### Вопрос 2: Какие факторы заставляют переменную "убежать" в кучу?

**Ответ**: Основные факторы:

- Возврат указателя на локальную переменную
- Хранение в интерфейсе (interface{})
- Захват замыканием или горутиной
- Хранение в глобальной переменной или структуре с большим временем жизни
- Передача в канал
- Слишком большой размер объекта

### Вопрос 3: Как проверить, убегает ли переменная в кучу?

**Ответ**: Используйте флаг компилятора `-gcflags="-m"`:

```
go build -gcflags="-m" ./...
```

Для более детального анализа: `-gcflags="-m -m"`. Компилятор выведет сообщения типа "moved to heap: x" или "escapes to heap".

### Вопрос 4: Что быстрее — аллокация на стеке или в куче, и почему?

**Ответ**: Stack allocation значительно быстрее (в десятки раз) по нескольким причинам:

- Стек очищается автоматически при выходе из функции
- Не требуется работа GC
- Выделение памяти — это просто сдвиг указателя стека
- Heap allocation требует работы аллокатора и последующей очистки через GC, что создаёт накладные расходы

### Вопрос 5: Всегда ли возврат указателя приводит к escape?

**Ответ**: Не всегда. Компилятор достаточно умён и может оптимизировать код. Если компилятор видит, что указатель используется только локально и не расшаривается реально, он может оставить значение на стеке. Однако в большинстве случаев возврат указателя действительно вызывает escape.

### Вопрос 6: Как escape analysis связан с производительностью приложения?

**Ответ**: Escape analysis напрямую влияет на производительность:

- Меньше heap allocations → меньше работы для GC → меньше пауз и CPU overhead
- GC может использовать до 25% CPU capacity
- Heap allocations создают latency из-за "stop the world" пауз
- Stack allocations в 10-40 раз быстрее
- Правильная оптимизация может улучшить latency на 10-30%

### Вопрос 7: Что такое "GC pressure" и как escape analysis помогает её снизить?

**Ответ**: GC pressure — это нагрузка на сборщик мусора из-за количества объектов в куче, которые нужно отслеживать и очищать. Escape analysis помогает снизить её, определяя, какие объекты можно безопасно разместить на стеке. Меньше объектов в куче → меньше работы для GC → ниже GC pressure → лучше производительность.

### Вопрос 8: В каких случаях интерфейсы вызывают escape?

**Ответ**: Когда значение помещается в интерфейс (особенно `interface{}`), оно обычно убегает в кучу, потому что интерфейсы непрозрачны для компилятора — он не может точно определить время жизни значения и тип во время компиляции. Это одна из причин, почему частое использование `interface{}` может негативно влиять на производительность.

### Вопрос 9: Как замыкания (closures) влияют на escape analysis?

**Ответ**: Если замыкание захватывает переменную и может выполняться после завершения родительской функции (например, передаётся в горутину или возвращается), захваченные переменные убегают в кучу. Компилятор не может гарантировать, что переменная не будет использоваться после освобождения стека.

### Вопрос 10: Стоит ли всегда оптимизировать код для избежания escape?

**Ответ**: Нет. Оптимизация имеет смысл только в критичных к производительности участках:

- В горячих циклах и hot paths
- Когда профилирование показывает проблемы с GC
- Для коротко живущих объектов в высоконагруженных системах

Не стоит оптимизировать, если:

- Это конструкторы (идиоматично возвращать указатель)
- Объекты должны жить долго
- Аллокации редкие
- Оптимизация ухудшает читаемость кода

## Практические задания

### Задание 1: Анализ escape

Определите, какие переменные убегут в кучу, и проверьте с помощью компилятора:

```
package main

type User struct {
    Name  string
    Email string
}

func task1() User {
    u := User{Name: "Alice"}
    return u
}

func task2() *User {
    u := User{Name: "Bob"}
    return \&u
}

func task3() {
    u := User{Name: "Charlie"}
    process(\&u)
}

func process(u *User) {
    // просто использует указатель
}

func task4() func() string {
    name := "David"
    return func() string {
    return name
    }
}

var globalUser *User

func task5() {
    u := User{Name: "Eve"}
    globalUser = \&u
}
```

**Проверка**:

```
go run -gcflags="-m" main.go
```

**Ответы**:

- `task1`: `u` остаётся на стеке (value semantics)
- `task2`: `u` убегает в кучу (возврат указателя)
- `task3`: `u` остаётся на стеке (указатель не покидает scope)
- `task4`: `name` убегает в кучу (захват замыканием)
- `task5`: `u` убегает в кучу (хранение в глобальной переменной)

### Задание 2: Оптимизация функции

Оптимизируйте функцию для уменьшения heap allocations:

```
// До оптимизации
func createUsers(count int) []*User {
    users := make([]*User, count)
    for i := 0; i < count; i++ {
        u := \&User{Name: fmt.Sprintf("User%d", i)}
        users[i] = u
    }
    return users
}
```

**Подсказка**: Подумайте, действительно ли нужны указатели внутри слайса?

**Решение**:

```
// После оптимизации
func createUsers(count int) []User {
    users := make([]User, count)
    for i := 0; i < count; i++ {
        users[i] = User{Name: fmt.Sprintf("User%d", i)}
    }
    return users
}
```

Если размер `User` небольшой и не требуется расшаривание, value semantics эффективнее.

### Задание 3: Бенчмарк

Создайте бенчмарк для сравнения двух подходов:

```
package main

import "testing"

type Data struct {
    X, Y, Z int
}

func ValueReturn() Data {
    return Data{1, 2, 3}
}

func PointerReturn() *Data {
    return &Data{1, 2, 3}
}

func BenchmarkValue(b *testing.B) {
    for i := 0; i < b.N; i++ {
        _ = ValueReturn()
    }
}

func BenchmarkPointer(b *testing.B) {
    for i := 0; i < b.N; i++ {
        _ = PointerReturn()
    }
}
```

Запустите:

```
go test -bench=. -benchmem
```

Проанализируйте результаты: количество аллокаций и скорость.

### Задание 4: Реальный сценарий

Оптимизируйте HTTP handler:

```

// До
func HandleRequest(w http.ResponseWriter, r *http.Request) {
    resp := &Response{
        Status: "ok",
        Data:   processData(r),
    }
    json.NewEncoder(w).Encode(resp)
}

// Оптимизация
func HandleRequest(w http.ResponseWriter, r *http.Request) {
    resp := Response{  // value semantics
        Status: "ok",
        Data:   processData(r),
    }
    json.NewEncoder(w).Encode(&resp)  // расшариваем только для Encode
}
```
