Мьютекс (mutex, от англ. mutual exclusion — «взаимное исключение») — это примитив синхронизации в Go, который гарантирует, что в один момент времени только одна горутина может получить доступ к защищённому ресурсу. Мьютексы необходимы для предотвращения **race condition** (состояния гонки), когда несколько горутин одновременно пытаются читать и писать в общую переменную, что может привести к непредсказуемому поведению программы.

## Основные концепции

### Что такое race condition?

Race condition возникает, когда две или более горутины одновременно обращаются к одной и той же переменной, и **хотя бы одна из них её изменяет**. Представьте что у нас есть `var counter int` и внутри двух горутин происходит `counter++`.

Внутри операция `counter++` на самом деле состоит из трёх шагов:

1. Прочитать текущее значение
2. Увеличить его на 1
3. Записать результат обратно

> Это крайне важно понимать!

В компиляторе, в ассемблере выглядит примерно так:

```
; 1) Чтение значения из памяти в регистр
MOVQ counter(%rip), %rax ; LOAD: загрузить значение из памяти в регистр RAX

; 2) Увеличение значения в регистре
ADDQ $1, %rax            ; ADD: прибавить 1 к значению в RAX

; 3) Запись результата обратно в память
MOVQ %rax, counter(%rip) ; STORE: записать значение из RAX обратно в память
```

Если две горутины выполняют эти шаги одновременно (обе делают 1, потом обе делают 2, потом обе 3) , они могут перезаписать результаты друг друга.

### Критическая секция

> Критическая секция — это участок кода, где горутина обращается к общим ресурсам. Мьютекс обеспечивает, что только одна горутина может находиться в критической секции в один момент времени.

## Пакет sync и его основные типы

В Go мьютексы находятся в пакете `sync`. Стандартная библиотека предоставляет два основных типа мьютексов:

### sync.Mutex

`Mutex` (обычный мьютекс) — это самый простой тип блокировки. Он не различает операции чтения и записи, поэтому **в один момент времени только одна горутина может получить доступ к защищённому ресурсу, независимо от типа операции**.

**Основные методы:**

- `Lock()` — блокирует мьютекс. Если он уже заблокирован другой горутиной, текущая горутина будет ждать.
- `Unlock()` — разблокирует мьютекс, позволяя другой горутине получить доступ.

**Пример использования:**

```go
package main

import (
    "fmt"
    "sync"
)

var (
    counter int
    mu      sync.Mutex
)

func increment() {
    mu.Lock()
    defer mu.Unlock()
    counter++
}

func main() {
    var wg sync.WaitGroup

    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            increment()
        }()
    }

    wg.Wait()
    fmt.Println("Counter:", counter) // Всегда будет 1000
}
```

Ключевая особенность: используется паттерн `defer mu.Unlock()` сразу после `Lock()`, чтобы гарантировать разблокировку даже если произойдёт panic.

### sync.RWMutex

`RWMutex` (read-write mutex) — более продвинутый мьютекс, который различает операции чтения (read) и записи (write). **Несколько горутин могут одновременно читать данные, но когда одна горутина *записывает*, все остальные должны ждать**.

**Основные методы:**

- `RLock()` — блокирует мьютекс для чтения. Может быть вызван одновременно несколькими горутинами.
- `RUnlock()` — разблокирует читательскую блокировку.
- `Lock()` — блокирует мьютекс для записи. Исключает все остальные горутины.
- `Unlock()` — разблокирует писательскую блокировку.

**Пример использования:**

Тут главное понять идею

```go
package main

import (
    "fmt"
    "sync"
)

type UserCache struct {
    mu    sync.RWMutex
    users map[string]string
}

func (uc *UserCache) Get(key string) string {
    uc.mu.RLock()
    defer uc.mu.RUnlock()
    return uc.users[key]
}

func (uc *UserCache) Set(key, value string) {
    uc.mu.Lock()
    defer uc.mu.Unlock()
    uc.users[key] = value
}

func main() {
    cache := &UserCache{users: make(map[string]string)}

    // Множество горутин могут одновременно читать
    for i := 0; i < 5; i++ {
        go func() {
            fmt.Println(cache.Get("user1"))
        }()
    }

    // Писатель должен ждать
    cache.Set("user1", "John")
}
```

RWMutex оптимален в сценариях, где данные часто читаются, но редко изменяются. Например, 70-80% чтения, остальное запись -- такое нам подходит.

## Внутреннее устройство мьютексов в Go

### Структура sync.Mutex

На низком уровне `sync.Mutex` представляет собой структуру, содержащую целое число, которое хранит состояние мьютекса:

```go
type Mutex struct {
    state int32  // Cостояние блокировки
    sema  uint32 // Семафор для управления ожидающими горутинами
}
```

### Битовое представление состояния

Целое число `state` использует свои биты для кодирования различной информации:

Это не надо учить, но полезно +- запомнить:

- **Бит 0 (locked)**: 1, если мьютекс заблокирован, 0 если свободен.
- **Бит 1 (woken)**: 1, если горутина была пробуждена и может захватить блокировку.
- **Бит 2 (starving)**: 1, если мьютекс находится в режиме "голода" (длительное ожидание горутин).
- **Оставшиеся биты**: счётчик ожидающих горутин.

### Семафор (Sema)

Поле `sema` — это семафор, который используется для управления ожидающими горутинами.

Когда горутина не может критическую секцию:

1. Она увеличивает счётчик ожидающих горутин в поле `state`
2. Засыпает
3. Когда другая горутина разблокирует мьютекс, она пробуждает одну из ожидающих горутин через системный вызов

### Особенности реализации

**Spinlock оптимизация**: Прежде чем вызвать системный вызов и заснуть, горутина может несколько раз попытаться захватить мьютекс в цикле (spinlock). Это полезно, если мьютекс освободится через очень короткое время, избегая дорогостоящего переключения контекста.

**Режим голода (Starving mode)**: Если горутина ждёт слишком долго, мьютекс переходит в режим голода, где:

- Новые приходящие горутины не пытаются захватить мьютекс напрямую.
- Мьютекс напрямую передаётся следующей ожидающей горутине.
- Это предотвращает ситуацию, когда старые горутины никогда не получают доступ.

## Правильное использование мьютексов

### Общие принципы

1. **Минимальная критическая секция**: Держите блокировку как можно короче. Выполняйте всё остальное кода вне мьютекса.

```go
// Плохо: долгая операция в критической секции
mu.Lock()
result := expensiveComputation()
mu.Unlock()
log.Print(result) // Должно быть вне блокировки

// Хорошо: быстрая операция в критической секции
result := expensiveComputation()
mu.Lock()
counter += result
mu.Unlock()
log.Print(counter)
```

Не надо например логи в крит. секции писать))

2. **Всегда используйте defer для разблокировки**: Гарантирует разблокировку даже при панике.

```go
mu.Lock()
defer mu.Unlock()
// Ваш код
```

3. **Мьютекс не должен копироваться**: Мьютекс содержит внутреннее состояние, которое не должно дублироваться. Передавайте **структуры с мьютексом через указатель**.

```go
// Плохо
type Config struct {
    mu    sync.Mutex
    data  map[string]string
}

func process(c Config) { // Копирует мьютекс!
    c.mu.Lock()
    // ...
}

// Хорошо
func process(c *Config) { // Передаёт указатель
    c.mu.Lock()
    // ...
}
```

4. **Избегайте вложенных блокировок (deadlock)**: Если вам нужны две блокировки, всегда захватывайте их в одном порядке. Взаимная блокировка (deadlock) возникает, когда две горутины ждут друг друга.

```go
// Опасно! Может привести к deadlock
var mu1, mu2 sync.Mutex

func A() {
    mu1.Lock()
    defer mu1.Unlock()
    mu2.Lock()
    defer mu2.Unlock()
    // ...
}

func B() {
    mu2.Lock()
    defer mu2.Unlock()
    mu1.Lock()
    defer mu1.Unlock()
    // ...
}

// Если A захватит mu1, а B захватит mu2, они будут ждать друг друга навсегда
```

**Разный порядок (DEADLOCK):**

- Горутина A: захватывает mu1 → ждёт mu2
- Горутина B: захватывает mu2 → ждёт mu1
Результат: A держит mu1 и не может получить mu2 (его держит B). B держит mu2 и не может получить mu1 (его держит A). Обе горутины ждут вечно.

**Одинаковый порядок (БЕЗ DEADLOCK):**

- Горутина A: захватывает mu1 → захватывает mu2 → освобождает оба
- Горутина B: ждёт mu1 → захватывает mu1 → захватывает mu2 → освобождает оба
Результат: B просто ждёт, пока A освободит mu1, затем спокойно захватывает оба мьютекса в том же порядке. Циклического ожидания не возникает.

5. **Выбор между Mutex и RWMutex**: Используйте `RWMutex`, если:
   - Данные часто читаются (много чтений).
   - Данные редко изменяются (мало записей).
   - Конкуренция читателей высока.

В противном случае обычный `Mutex` может быть более эффективным.

### Вложение мьютекса в структуру

Обычно мьютекс встраивается прямо в структуру, которую он защищает:

```go
type Account struct {
    mu      sync.Mutex
    balance float64
}

func (a *Account) Deposit(amount float64) {
    a.mu.Lock()
    defer a.mu.Unlock()
    a.balance += amount
}

func (a *Account) Withdraw(amount float64) bool {
    a.mu.Lock()
    defer a.mu.Unlock()
    if a.balance >= amount {
        a.balance -= amount
        return true
    }
    return false
}
```

## Альтернативы и связанные примитивы

### sync.WaitGroup

`WaitGroup` используется для ожидания завершения группы горутин. Это не мьютекс, но часто используется вместе с ними.

```go
var wg sync.WaitGroup

for i := 0; i < 10; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        // Работа
    }()
}

wg.Wait() // Ждём завершения всех горутин
```

### sync.Once

`Once` гарантирует, что функция выполнится только один раз, даже если вызвать её из множества горутин:

```go
var once sync.Once
var instance *Singleton

func GetInstance() *Singleton {
    once.Do(func() {
        instance = &Singleton{}
    })
    return instance
}
```

### Каналы

Go предоставляет каналы как альтернативу мьютексам для синхронизации. Часто каналы предпочтительнее для управления потоком выполнения.

```go
func worker(jobs <-chan int, results chan<- int) {
    for job := range jobs {
        results <- job * 2
    }
}
```

## Диагностика проблем

### Использование go run -race

Go включает встроенный детектор race condition. Запустите программу с флагом `-race` для обнаружения гонок данных:

```bash
go run -race main.go
```

Это замедлит программу и добавит проверки, но поймает большинство проблем конкурентности.

### Типичные ошибки

1. **Забытый Unlock**: Привести к взаимной блокировке всей программы.
2. **Копирование мьютекса**: Каждая копия будет иметь своё состояние.
3. **Чтение без блокировки**: Race condition и непредсказуемые значения.
4. **Слишком долгая критическая секция**: Снижение параллелизма и производительности.

## Частые вопросы на собеседованиях

### 1. В чём разница между sync.Mutex и sync.RWMutex?

**Ответ**: `Mutex` полностью блокирует доступ — только одна горутина может работать с ресурсом. `RWMutex` различает чтение и запись: множество горутин могут одновременно читать, но когда пишут, никто не может ни читать, ни писать. RWMutex оптимален для сценариев с частыми чтениями и редкими записями.

### 2. Что такое race condition и как её избежать?

**Ответ**: Race condition возникает, когда несколько горутин одновременно обращаются к одной переменной и модифицируют её. Избежать этого можно:

- Использовать мьютексы для синхронизации доступа.
- Использовать каналы для передачи данных между горутинами.
- Избегать общего состояния, где это возможно.

Проверить наличие race condition можно с помощью `go run -race`.

### 3. Может ли горутина дважды заблокировать один мьютекс?

**Ответ**: Нет, `sync.Mutex` не рекурсивен. Если горутина попытается заблокировать один и тот же мьютекс дважды, она заблокируется (deadlock). Это особенность дизайна Go — рекурсивные мьютексы сложнее в использовании и часто скрывают проблемы в коде.

### 4. Что такое deadlock и как его избежать?

**Ответ**: Deadlock (взаимная блокировка) возникает, когда две или более горутины ждут друг друга и никогда не смогут продолжить. Типичный пример:

- Горутина A захватила мьютекс 1 и ждёт мьютекса 2.
- Горутина B захватила мьютекс 2 и ждёт мьютекса 1.

Избежать deadlock:

- Всегда захватывайте несколько мьютексов в одном порядке.
- Минимизируйте время блокировки.
- Используйте таймауты где возможно.

### 5. Как работает внутри sync.Mutex?

**Ответ**: На низком уровне `Mutex` использует целое число для хранения состояния (заблокирован/разблокирован, количество ожидающих горутин, режим голода) и семафор для управления ожидающими горутинами. Когда горутина не может захватить блокировку:

1. Сначала пытается несколько раз в цикле (spinlock).
2. Затем вызывает системный вызов `futex` (на Linux) и засыпает.
3. Когда другая горутина разблокирует мьютекс, она пробуждает одну из ожидающих горутин.

### 6. Почему мьютекс нельзя копировать?

**Ответ**: `Mutex` содержит внутреннее состояние (кто заблокировал, сколько ожидают). При копировании каждая копия будет иметь независимое состояние. Если функция случайно скопирует структуру с мьютексом, блокировки перестанут работать как ожидается. Go это предотвращает, давая ошибку при попытке скопировать мьютекс.

### 7. Когда использовать Mutex вместо каналов?

**Ответ**:

- **Используйте Mutex**: Для защиты общего состояния, когда несколько горутин должны читать/писать в одну структуру данных (счётчик, кэш, конфигурация).
- **Используйте каналы**: Для передачи данных между горутинами, координации задач, потоков выполнения (producer-consumer).

Философия Go: "Общайтесь через каналы, синхронизируйте через мьютексы".

### 8. Что произойдёт, если разблокировать незаблокированный мьютекс?

**Ответ**: Программа упадёт с паникой: `sync: unlock of unlocked mutex`. Это ошибка программиста.

### 9. Может ли yield после Lock улучшить производительность?

**Ответ**: Обычно нет. `sync.Mutex` уже содержит spinlock оптимизацию, которая пытается несколько раз перед засыпанием. Добавление явного yield часто замедляет, а не ускоряет программу.

### 10. Как отладить проблемы с мьютексами?

**Ответ**:

- `go run -race` для обнаружения race condition.
- `pprof` для профилирования блокировок и выявления узких мест.
- Логирование моментов Lock/Unlock (осторожно с перформансом).
- Анализ deadlock через логи goroutine (runtime/debug.PrintStack).

## Практические упражнения

### Упражнение 1: Безопасный счётчик

Напишите функцию, которая инкрементирует счётчик из множества горутин. Убедитесь, что финальное значение правильное.

**Требования:**

- Используйте `sync.Mutex` для защиты счётчика.
- Запустите 1000 горутин.
- Каждая горутина должна инкрементировать счётчик 100 раз.
- Финальное значение должно быть 100000.

**Решение:**

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    var counter int
    var mu sync.Mutex
    var wg sync.WaitGroup

    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := 0; j < 100; j++ {
                mu.Lock()
                counter++
                mu.Unlock()
            }
        }()
    }

    wg.Wait()
    fmt.Println("Counter:", counter)
}
```

### Упражнение 2: Кэш с RWMutex

Напишите кэш, который хранит пары ключ-значение. Оптимизируйте для частых чтений и редких записей.

**Требования:**

- Используйте `sync.RWMutex`.
- Методы `Get(key string)` и `Set(key, value string)`.
- Запустите 10 горутин для чтения и 2 для записи.
- Убедитесь, что чтения не блокируют друг друга.

**Решение:**

```go
package main

import (
    "fmt"
    "sync"
    "time"
)

type Cache struct {
    mu    sync.RWMutex
    data  map[string]string
}

func (c *Cache) Get(key string) string {
    c.mu.RLock()
    defer c.mu.RUnlock()
    return c.data[key]
}

func (c *Cache) Set(key, value string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.data[key] = value
}

func main() {
    cache := &Cache{data: make(map[string]string)}

    var wg sync.WaitGroup

    // Читатели
    for i := 0; i < 10; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            for j := 0; j < 5; j++ {
                val := cache.Get("key1")
                fmt.Printf("Reader %d: %s\n", id, val)
                time.Sleep(10 * time.Millisecond)
            }
        }(i)
    }

    // Писатели
    for i := 0; i < 2; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            for j := 0; j < 3; j++ {
                cache.Set("key1", fmt.Sprintf("value_%d_%d", id, j))
                fmt.Printf("Writer %d: wrote\n", id)
                time.Sleep(50 * time.Millisecond)
            }
        }(i)
    }

    wg.Wait()
    fmt.Println("Final value:", cache.Get("key1"))
}
```

### Упражнение 3: Обнаружение и исправление deadlock

Исправьте следующий код, который вызывает deadlock:

**Проблемный код:**

```go
package main

import (
    "fmt"
    "sync"
)

var mu1, mu2 sync.Mutex

func taskA() {
    mu1.Lock()
    fmt.Println("A locked mu1")
    mu2.Lock()
    fmt.Println("A locked mu2")
    mu2.Unlock()
    mu1.Unlock()
}

func taskB() {
    mu2.Lock()
    fmt.Println("B locked mu2")
    mu1.Lock()
    fmt.Println("B locked mu1")
    mu1.Unlock()
    mu2.Unlock()
}

func main() {
    go taskA()
    go taskB()
    select{}
}
```

**Решение:** Захватывать мьютексы в одном порядке:

```go
package main

import (
    "fmt"
    "sync"
)

var mu1, mu2 sync.Mutex

func taskA() {
    mu1.Lock()
    defer mu1.Unlock()
    fmt.Println("A locked mu1")
    mu2.Lock()
    defer mu2.Unlock()
    fmt.Println("A locked mu2")
}

func taskB() {
    mu1.Lock()  // Захватываем в том же порядке!
    defer mu1.Unlock()
    fmt.Println("B locked mu1")
    mu2.Lock()
    defer mu2.Unlock()
    fmt.Println("B locked mu2")
}

func main() {
    var wg sync.WaitGroup
    wg.Add(2)

    go func() {
        defer wg.Done()
        taskA()
    }()

    go func() {
        defer wg.Done()
        taskB()
    }()

    wg.Wait()
}
```

### Упражнение 4: Использование go run -race

### Упражнение 5: Банковская система

Напишите систему банковских счётов с возможностью безопасных переводов между счётами.

**Требования:**

- Структура `Account` с балансом, защищённым мьютексом.
- Метод `Transfer(from, to *Account, amount float64)` для переводов.
- Проверьте, что сумма денег в системе сохраняется.
- Используйте правильный порядок захвата мьютексов, чтобы избежать deadlock.

**Решение:**

```go
package main

import (
    "fmt"
    "sync"
)

type Account struct {
    id      int
    mu      sync.Mutex
    balance float64
}

func (a *Account) Transfer(to *Account, amount float64) bool {
    // Захватываем в порядке по ID, чтобы избежать deadlock
    var first, second *Account
    if a.id < to.id {
        first, second = a, to
    } else {
        first, second = to, a
    }

    first.mu.Lock()
    defer first.mu.Unlock()
    second.mu.Lock()
    defer second.mu.Unlock()

    if a.balance >= amount {
        a.balance -= amount
        to.balance += amount
        return true
    }
    return false
}

func main() {
    acc1 := &Account{id: 1, balance: 1000}
    acc2 := &Account{id: 2, balance: 1000}

    var wg sync.WaitGroup

    // Множество переводов
    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            if i%2 == 0 {
                acc1.Transfer(acc2, 10)
            } else {
                acc2.Transfer(acc1, 10)
            }
        }()
    }

    wg.Wait()

    totalBalance := acc1.balance + acc2.balance
    fmt.Printf("Account 1: %.2f\n", acc1.balance)
    fmt.Printf("Account 2: %.2f\n", acc2.balance)
    fmt.Printf("Total: %.2f (должно быть 2000)\n", totalBalance)
}
```

## Заключение

Мьютексы — это фундаментальный инструмент для написания безопасного конкурентного кода на Go. Ключевые моменты:

1. **Мьютекс защищает ресурс**: Только одна горутина в один момент может работать в критической секции.
2. **RWMutex оптимален для чтений**: Используйте его, если читаются данные чаще, чем пишутся.
3. **Спроектируйте правильно**: Минимизируйте критическую секцию, избегайте deadlock, не копируйте мьютекс.
4. **Тестируйте с -race**: Обнаруживайте race condition на ранних этапах.
5. **Рассмотрите альтернативы**: Каналы часто более элегантны для синхронизации потоков выполнения.

Глубокое понимание мьютексов поможет вам написать масштабируемый и надёжный код на Go.
