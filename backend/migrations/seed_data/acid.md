ACID — это набор свойств, гарантирующих надежность транзакций в базах данных. Понимание ACID особенно важно при работе с реляционными базами данных.

## Что такое транзакция

Транзакция - последовательность операций с БД, которые выполняются как единое целое. Все операции внутри транзакции либо завершаются успешно, либо отменяются полностью. "Нельзя перепрыгнуть пропасть на 99%".

В Go транзакция создается через пакет `database/sql` и представлена типом `sql.Tx`.

## Свойства ACID

### Atomicity (Атомарность)

Атомарность означает, что транзакция... атомарна. Либо все операции внутри транзакции выполняются успешно, либо не выполняется ни одна. Не существует промежуточного состояния, когда часть операций выполнена, а часть нет.

**Пример ситуации:** При переводе денег между счетами нужно снять деньги с одного счета и зачислить на другой. Если после списания произойдет ошибка, атомарность гарантирует откат всех изменений. Потому что если с одного человека деньги сняли, а другому не перевели - это неправильно.

**Как это работает в Go:**
(синтаксис похож на тот, что в SQL)

- Если одна из операций в транзакции возвращает ошибку, вызывается `Rollback()`
- Все изменения откатываются, база данных возвращается в исходное состояние
- Только при успешном завершении всех операций вызывается `Commit()`

### Consistency (Согласованность)

Согласованность гарантирует, что транзакция переводит базу данных из одного **валидного** состояния в другое **валидное** состояние. Все правила целостности данных должны соблюдаться. Вас часто могу спрашивать на собесах - а какие правила целостности?

**Вот они:**

- Ограничения (constraints)
- Внешние ключи (foreign keys)
- Уникальные индексы
- Триггеры базы данных
- Правила валидации на уровне приложения

**Важно:** Если транзакция нарушает правила согласованности, она должна быть отклонена, и изменения не должны быть применены.

### Isolation (Изолированность)

Представьте, что у вас идет несколько параллельных транзакций. Должны ли они быть изолированны друг от друга? Если да, то полностью? Или при каких-то условиях нам надо понимать, какая еще модификация происходит у наших данных?

Изолированность определяет, как и когда изменения, сделанные одной транзакцией, становятся видимыми для других параллельных транзакций. Это предотвращает возникновение гонки данных при одновременной работе нескольких транзакций.

**Аномалии параллельных транзакций:**

- **Dirty Read** — чтение незафиксированных данных другой транзакции
- **Non-repeatable Read** — повторное чтение возвращает другое значение из-за изменений другой транзакцией
- **Phantom Read** — при повторном запросе появляются новые строки, добавленные другой транзакцией
- **Serialization Anomaly** — результат параллельного выполнения транзакций невозможен при последовательном выполнении

На них есть отдельная заметка. Ну и ниже рассмотрим.

### Durability (Долговечность)

Долговечность гарантирует, что после успешного завершения транзакции (commit) все внесенные изменения сохраняются постоянно, даже в случае сбоя системы, отключения питания или других катастрофических событий.

**Механизмы обеспечения:**

- Запись в журнал транзакций (transaction log)
- Просто пишем на диск (WAL - загугли)
- Репликация данных
- Резервное копирование

## Уровни изоляции транзакций

SQL стандарт определяет четыре уровня изоляции транзакций, каждый из которых предотвращает определенные проблемы параллельного доступа.

### Read Uncommitted

Самый низкий уровень изоляции. **Транзакция может читать незафиксированные изменения других транзакций**.

**Проблемы:** Допускает Dirty Read, Non-repeatable Read, Phantom Read

**Применение:** Редко используется из-за низкой надежности.

### Read Committed

Транзакция видит только зафиксированные изменения других транзакций. **Это уровень по умолчанию в PostgreSQL**.

**Проблемы:** Предотвращает Dirty Read, но допускает Non-repeatable Read и Phantom Read

**Применение:** Подходит для большинства веб-приложений с обычной нагрузкой.

### Repeatable Read

Гарантирует, что если транзакция читает строку дважды, она получит одинаковые данные. Другие транзакции не могут изменить уже прочитанные строки.

**Проблемы:** Предотвращает Dirty Read и Non-repeatable Read, но допускает Phantom Read

**Применение:** Используется для операций, требующих консистентного чтения данных.

### Serializable

Самый строгий уровень изоляции. Транзакции выполняются так, как будто они выполняются последовательно, одна за другой.

**Проблемы:** Предотвращает все проблемы параллельного доступа

**Применение:** Критически важные операции с финансовыми данными или когда требуется полная изоляция.

## Реализация транзакций в Go

### Базовый паттерн

```go
func transferMoney(db *sql.DB, fromAccount, toAccount int, amount float64) error {
    // Начало транзакции
    tx, err := db.BeginTx(context.Background(), nil)
    if err != nil {
        return err
    }

    // Автоматический откат при ошибке
    defer tx.Rollback()

    // Списание со счета отправителя
    _, err = tx.Exec("UPDATE accounts SET balance = balance - ? WHERE id = ?", amount, fromAccount)
    if err != nil {
        return err
    }

    // Зачисление на счет получателя
    _, err = tx.Exec("UPDATE accounts SET balance = balance + ? WHERE id = ?", amount, toAccount)
    if err != nil {
        return err
    }

    // Фиксация транзакции
    return tx.Commit()
}
```

### Установка уровня изоляции

```go
func createTransaction(db *sql.DB) error {
    // Настройка уровня изоляции
    tx, err := db.BeginTx(context.Background(), &sql.TxOptions{
        Isolation: sql.LevelSerializable,
        ReadOnly:  false,
    })
    if err != nil {
        return err
    }
    defer tx.Rollback()

    // Операции с базой данных
    // ...

    return tx.Commit()
}
```

### Продвинутый паттерн с обработкой ошибок

```go
func executeTransaction(db *sql.DB, txFunc func(*sql.Tx) error) error {
    tx, err := db.BeginTx(context.Background(), nil)
    if err != nil {
        return err
    }

    defer func() {
        if p := recover(); p != nil {
            tx.Rollback()
            panic(p) // Повторный выброс паники
        } else if err != nil {
            tx.Rollback()
        } else {
            err = tx.Commit()
        }
    }()

    err = txFunc(tx)
    return err
}

// Использование
err := executeTransaction(db, func(tx *sql.Tx) error {
    _, err := tx.Exec("INSERT INTO users (name) VALUES (?)", "John")
    if err != nil {
        return err
    }

    _, err = tx.Exec("INSERT INTO profiles (user_id, bio) VALUES (?, ?)", 1, "Developer")
    return err
})
```

## Важные термины

### Transaction ID

Уникальный идентификатор транзакции, используемый СУБД для отслеживания и управления транзакциями.

### Commit

Операция фиксации транзакции, делающая все изменения постоянными.

### Rollback

Операция отката транзакции, отменяющая все изменения, сделанные в рамках транзакции.

### Lock

Механизм блокировки, предотвращающий конфликты при одновременном доступе к данным.

### Deadlock

Ситуация взаимной блокировки, когда две или более транзакций ожидают освобождения ресурсов друг друга.

### MVCC (Multi-Version Concurrency Control)

Механизм контроля параллельного доступа с использованием нескольких версий данных, применяемый в PostgreSQL.

### Write-Ahead Logging (WAL)

Протокол записи изменений в журнал до их применения к основным данным, обеспечивающий долговечность.

### Two-Phase Commit (2PC)

Протокол для распределенных транзакций, гарантирующий атомарность операций на нескольких узлах.

## Частые вопросы на собеседованиях

### Теоретические вопросы

**1. Что означает каждая буква в ACID?**

- A — Atomicity (атомарность): все или ничего
- C — Consistency (согласованность): соблюдение правил целостности
- I — Isolation (изолированность): независимость параллельных транзакций
- D — Durability (долговечность): постоянство зафиксированных изменений

**2. В чем разница между Commit и Rollback?**
Commit фиксирует все изменения транзакции, делая их постоянными. Rollback отменяет все изменения, возвращая базу данных в состояние до начала транзакции.

**3. Какой уровень изоляции используется по умолчанию в PostgreSQL?**
Read Committed — транзакция видит только зафиксированные изменения других транзакций.

**4. Что такое Dirty Read?**
Чтение незафиксированных данных из другой транзакции, которая может быть отменена. Это может привести к чтению некорректных данных.

**5. Чем Repeatable Read отличается от Serializable?**
Repeatable Read предотвращает изменение уже прочитанных строк, но допускает появление новых строк (Phantom Read). Serializable предотвращает все аномалии параллельного выполнения.

**6. Почему важна атомарность при переводе денег?**
Атомарность гарантирует, что деньги не могут быть списаны без зачисления или наоборот. Либо обе операции выполняются, либо обе отменяются.

**7. Что произойдет, если вызвать Commit после Rollback?**
После Rollback транзакция становится невалидной. Попытка вызвать Commit вернет ошибку, так как транзакция уже завершена.

**8. Как база данных обеспечивает долговечность?**
Через механизм Write-Ahead Logging — все изменения сначала записываются в журнал транзакций на диске, затем применяются к данным.

**9. Что такое deadlock и как его избежать?**
Deadlock — взаимная блокировка транзакций. Избежать можно через:

- Единообразный порядок доступа к ресурсам
- Установка таймаутов на блокировки
- Использование более низких уровней изоляции
- Минимизация времени удержания блокировок

**10. Можно ли вложить одну транзакцию в другую в Go?**
Напрямую вложенные транзакции (nested transactions) не поддерживаются в database/sql. Можно использовать savepoints для эмуляции подобного поведения, но это зависит от драйвера базы данных.

### Практические вопросы

**1. Как правильно обработать ошибку транзакции в Go?**

```go
tx, err := db.BeginTx(ctx, nil)
if err != nil {
    return err
}
defer tx.Rollback() // Откат, если Commit не был вызван

// Выполнение операций
if err := doSomething(tx); err != nil {
    return err // Rollback сработает через defer
}

return tx.Commit() // Успешная фиксация
```

**2. Зачем нужен defer tx.Rollback()?**
Это гарантирует, что транзакция будет откатана в случае любой ошибки или паники. Если Commit выполнен успешно, повторный Rollback не вызовет проблем.

**3. Как установить таймаут для транзакции?**

```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()

tx, err := db.BeginTx(ctx, nil)
// Транзакция автоматически откатится при истечении таймаута
```

**4. Почему нельзя использовать db.Query внутри транзакции?**
Внутри транзакции нужно использовать методы tx.Query, tx.Exec, tx.QueryRow, чтобы операции выполнялись в контексте транзакции. Использование db.Query создаст отдельное соединение вне транзакции.

**5. Как проверить, успешно ли зафиксирована транзакция?**

```go
if err := tx.Commit(); err != nil {
    // Транзакция не была зафиксирована
    // Нельзя использовать результаты операций
    return err
}
// Транзакция успешно зафиксирована
```

## Практические задачи

### Задача 1: Базовый перевод средств

Реализуйте функцию перевода денег между счетами с проверкой баланса:

```go
func transferWithValidation(db *sql.DB, fromID, toID int, amount float64) error {
    if amount <= 0 {
        return errors.New("amount must be positive")
    }

    tx, err := db.BeginTx(context.Background(), nil)
    if err != nil {
        return err
    }
    defer tx.Rollback()

    // Проверка баланса
    var balance float64
    err = tx.QueryRow("SELECT balance FROM accounts WHERE id = ? FOR UPDATE", fromID).Scan(&balance)
    if err != nil {
        return err
    }

    if balance < amount {
        return errors.New("insufficient funds")
    }

    // Списание
    _, err = tx.Exec("UPDATE accounts SET balance = balance - ? WHERE id = ?", amount, fromID)
    if err != nil {
        return err
    }

    // Зачисление
    _, err = tx.Exec("UPDATE accounts SET balance = balance + ? WHERE id = ?", amount, toID)
    if err != nil {
        return err
    }

    return tx.Commit()
}
```

**Ключевые моменты:**

- `FOR UPDATE` блокирует строку для изменения
- Проверка баланса до списания
- Использование defer для автоматического отката

### Задача 2: Массовая вставка с обработкой ошибок

```go
func insertMultipleUsers(db *sql.DB, users []User) error {
    tx, err := db.BeginTx(context.Background(), nil)
    if err != nil {
        return err
    }
    defer tx.Rollback()

    stmt, err := tx.Prepare("INSERT INTO users (name, email) VALUES (?, ?)")
    if err != nil {
        return err
    }
    defer stmt.Close()

    for _, user := range users {
        _, err := stmt.Exec(user.Name, user.Email)
        if err != nil {
            return fmt.Errorf("failed to insert user %s: %w", user.Name, err)
        }
    }

    return tx.Commit()
}
```

**Ключевые моменты:**

- Использование Prepare для оптимизации множественных вставок
- Откат всех вставок при ошибке любой из них
- Правильное закрытие statement

### Задача 3: Транзакция с разными уровнями изоляции

```go
func readWithIsolation(db *sql.DB, level sql.IsolationLevel) ([]User, error) {
    tx, err := db.BeginTx(context.Background(), &sql.TxOptions{
        Isolation: level,
        ReadOnly:  true,
    })
    if err != nil {
        return nil, err
    }
    defer tx.Rollback()

    rows, err := tx.Query("SELECT id, name, email FROM users")
    if err != nil {
        return nil, err
    }
    defer rows.Close()

    var users []User
    for rows.Next() {
        var user User
        if err := rows.Scan(&user.ID, &user.Name, &user.Email); err != nil {
            return nil, err
        }
        users = append(users, user)
    }

    if err := rows.Err(); err != nil {
        return nil, err
    }

    // Для read-only транзакций Commit все равно нужен
    if err := tx.Commit(); err != nil {
        return nil, err
    }

    return users, nil
}
```

**Ключевые моменты:**

- Параметр ReadOnly оптимизирует производительность
- Даже read-only транзакции требуют Commit
- Выбор уровня изоляции влияет на видимость данных

### Задача 4: Обработка deadlock

```go
func transferWithRetry(db *sql.DB, fromID, toID int, amount float64, maxRetries int) error {
    for i := 0; i < maxRetries; i++ {
        err := transferMoney(db, fromID, toID, amount)
        if err == nil {
            return nil
        }

        // Проверка на deadlock (код ошибки зависит от БД)
        if isDeadlockError(err) {
            time.Sleep(time.Millisecond * time.Duration(rand.Intn(100)))
            continue
        }

        return err
    }

    return errors.New("max retries exceeded due to deadlock")
}

func isDeadlockError(err error) bool {
    // Для PostgreSQL
    if pqErr, ok := err.(*pq.Error); ok {
        return pqErr.Code == "40P01" // deadlock_detected
    }
    return false
}
```

**Ключевые моменты:**

- Retry logic для обработки deadlock
- Экспоненциальная задержка между попытками
- Ограничение количества попыток

## Best Practices

### 1. Всегда используйте defer для Rollback

Это гарантирует откат при любых ошибках и паниках.

### 2. Держите транзакции короткими

Длинные транзакции увеличивают вероятность конфликтов и блокировок.

### 3. Используйте контекст с таймаутом

Предотвращает зависание транзакций.

### 4. Правильно выбирайте уровень изоляции

Более высокие уровни безопаснее, но медленнее. Используйте минимально необходимый.

### 5. Не смешивайте db и tx операции

Внутри транзакции используйте только методы tx.

### 6. Обрабатывайте ошибки Commit

Даже если операции выполнены, Commit может завершиться ошибкой.

### 7. Используйте FOR UPDATE для блокировок

При изменении данных на основе их текущего значения.

### 8. Тестируйте параллельные транзакции

Проблемы изоляции проявляются только при конкурентном доступе.

### 9. Логируйте транзакции

Для отладки и мониторинга производительности.

### 10. Используйте prepared statements

Для повторяющихся операций внутри транзакции.
