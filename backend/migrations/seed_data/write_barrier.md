Write Barrier (барьер записи) — это критически важный механизм сборщика мусора в Go, который обеспечивает корректность данных при конкурентной сборке мусора. Этот механизм позволяет сборщику работать параллельно с программой, минимизируя время остановки приложения.

## Что такое Write Barrier

Write Barrier представляет собой небольшую функцию, которая автоматически вызывается при каждом изменении указателей в heap-памяти. Основная задача — уведомить сборщик мусора об изменениях ссылок между объектами во время фазы marking, чтобы предотвратить преждевременную очистку достижимых объектов.

### Ключевые термины

- **Tricolor marking algorithm** — трёхцветный алгоритм разметки объектов
- **Concurrent GC** — параллельная сборка мусора
- **STW (Stop The World)** — остановка всех goroutine
- **Mark phase** — фаза разметки объектов
- **Heap invariants** — инварианты кучи
- **Root objects** — корневые объекты (глобальные переменные, стек)

## Проблема, которую решает Write Barrier

Представим ситуацию: сборщик мусора помечает объект A как "обработанный" (black), а затем программа создаёт новую ссылку A → C, где объект C пока не обработан (white). Без write barrier сборщик мусора может пропустить объект C и ошибочно удалить его, хотя он достижим через A.

> Пример проблемы без write barrier
>
> 1. GC уже обработал объект A (black)
> 2. Программа выполняет: A.field = C
> 3. Объект C остается white и может быть удален

## Трёхцветный алгоритм и Write Barrier

Go использует **tricolor mark-and-sweep** алгоритм с тремя цветами объектов:

- **White (белый)** — не проверенные объекты, потенциальный мусор
- **Gray (серый)** — объекты в очереди на обработку, достижимы но не проверены
- **Black (чёрный)** — обработанные объекты, гарантированно живые

### Weak Tricolor Invariant

Я б это не запоминал. Но прочитайте пару раз: Write barrier поддерживает слабый трёхцветный инвариант: **все белые объекты, достижимые из чёрных, должны быть также достижимы из серых объектов**. Это обеспечивает корректность сборки мусора при concurrent выполнении.

## Виды Write Barrier в Go

### Insertion Write Barrier (Dijkstra)

Помечает новый объект как серый при создании ссылки на него:

```
writePointer(slot, ptr):
    shade(ptr)  // пометить новый объект
    *slot = ptr
```

### Deletion Write Barrier (Yuasa)

Помечает удаляемый объект как серый:

```
writePointer(slot, ptr):
    shade(*slot)  // пометить старый объект  
    *slot = ptr
```

### Hybrid Write Barrier (Go 1.8+)

Комбинирует преимущества обоих подходов:

```
writePointer(slot, ptr):
    shade(*slot)  // deletion barrier
    shade(ptr)    // insertion barrier  
    *slot = ptr
```

## Реализация в Go

Компилятор автоматически внедряет проверки write barrier для операций с heap-объектами:

Просто увидьте что это рабтает на уровне ассемблера

```assembly
CMPL runtime.writeBarrier(SB), $0
JNE slow_path
MOVQ CX, "".sink(SB)        ; быстрый путь
JMP done
slow_path:
CALL runtime.gcWriteBarrierCX ; медленный путь с barrier
done:
```

### Когда активируется Write Barrier

Write barrier включается только во время **concurrent marking phase** сборки мусора. В остальное время проверка `runtime.writeBarrier` возвращает 0, и код выполняется по быстрому пути без дополнительных накладных расходов.

## Фазы сборки мусора с Write Barrier

Не надо учить. Поймите один раз.

### Mark Setup (STW)

- Включение write barrier для всех P (processors)
- Инициализация корневых объектов
- Время: 10-30 микросекунд

### Marking (Concurrent)

- Write barrier активен и отслеживает изменения
- Параллельная разметка объектов
- Возможны **Mark Assist** операции

### Mark Termination (STW)

- Отключение write barrier
- Финализация сборки мусора
- Время: 60-90 микросекунд

## Производительность и накладные расходы

### CPU накладные расходы

Каждая операция записи в heap требует дополнительной проверки — примерно 2 инструкции процессора. При активном write barrier выполняется вызов runtime функции в ассемблере для оптимальной производительности.

### Размер бинарника

Write barrier увеличивает размер исполняемого файла на 2-3% из-за внедрения проверок во все операции с указателями. Например, kubectl с отключенными write barrier был на 2MB (2.6%) меньше.

## Особенности реализации

### Стек vs Heap

Write barrier применяется **только к heap-объектам**, не к стеку. Это критично для производительности операций со стеком. В Go 1.8+ все стековые объекты помечаются как чёрные в начале GC для упрощения алгоритма.

### Buffer механизм

Go использует **write barrier buffer** для группировки изменений и снижения накладных расходов. При заполнении буфера происходит flush в runtime с сохранением всех регистров.

### Синхронизация

Write barrier синхронизируется через STW точки — когда все P остановлены, изменения `runtime.writeBarrier` становятся видимы всем процессорам одновременно.

## Настройка и мониторинг

### GC Trace

Для мониторинга write barrier используйте:

```bash
GODEBUG=gctrace=1 ./app
```

### GC Percentage

Параметр `GOGC` влияет на частоту срабатывания write barrier. По умолчанию 100% — следующая сборка запускается при удвоении live heap.

## Оптимизация работы с Write Barrier

### Минимизация heap-аллокаций

- Используйте value types вместо pointer types где возможно
- Применяйте object pooling для частых аллокаций
- Избегайте создания указателей в циклах

### Структуры данных

- Предпочитайте слайсы структур слайсам указателей
- Используйте встроенные типы вместо обёрток
- Минимизируйте количество указателей в структурах

## Частые вопросы на собеседованиях

### Базовые вопросы

**Q: Что такое write barrier в Go и зачем он нужен?**
A: Write barrier — это механизм, который отслеживает изменения указателей в heap-памяти во время concurrent garbage collection, обеспечивая корректность tricolor marking algorithm.

**Q: Когда активируется write barrier?**
A: Write barrier активируется только во время concurrent marking phase сборки мусора. В остальное время накладные расходы минимальны.

**Q: Какие виды write barrier используются в Go?**
A: С Go 1.8 используется hybrid write barrier, объединяющий Dijkstra insertion barrier и Yuasa deletion barrier для минимизации STW пауз.

### Продвинутые вопросы

**Q: Почему write barrier не применяется к стеку?**
A: Применение write barrier к стеку значительно замедлило бы все операции. Вместо этого Go в начале GC помечает все стековые объекты как чёрные.

**Q: Как write barrier влияет на производительность?**
A: Добавляет ~2 инструкции на каждую операцию записи указателя. При неактивном GC накладные расходы минимальны благодаря branch prediction.

**Q: Что произойдёт при отключении write barrier?**
A: Сборщик мусора будет работать некорректно, возможно удаление живых объектов. Программа может запуститься только с `GOGC=off`.

## Заключение

Write barrier — это сложный но эффективный механизм, позволяющий Go иметь низколатентный concurrent garbage collector. Понимание его работы критично для написания производительных Go-приложений и успешного прохождения собеседований на позиции Go-разработчика. Ключевые моменты для запоминания: tricolor invariants, hybrid barrier с Go 1.8, применение только к heap, и важность минимизации heap-аллокаций для оптимальной производительности.
